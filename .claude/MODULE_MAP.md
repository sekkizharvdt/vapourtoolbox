## Firestore admin access (for counting records — rule 31)

Service account key: **`docs/inputs/firebase-service-account-key.json`** (project
`vapour-toolbox`). Gitignored via the `inputs/` rule in `.gitignore:63` and not tracked — never
commit it, never print its contents. There is **no** key at `firebase-service-account.json` or
`mcp-servers/firebase-feedback/service-account-key.json`, despite older docs saying so.

Run one-off analysis scripts **from the repo root** (`node ./script.js`) so `firebase-admin`
resolves from the root `node_modules`; a script run from `/tmp` or the scratchpad fails with
`MODULE_NOT_FOUND`. Keep such scripts read-only and delete them after use, or add them under
`scripts/analysis/`.

`accounts` 110, `costCentres` 12, `projects` 11, `fixedAssets` 0.

### Notifications — one live system, two dead ones

Three notification implementations exist. Only one reaches a user:

- **LIVE:** `createTaskNotification` (`lib/tasks/taskNotificationService.ts`) → `taskNotifications` → `subscribeToUserTasks` (`lib/tasks/channelService.ts`) → **`/flow/inbox`**. Categories are `TaskNotificationCategory` in `@vapour/types/task.ts`; a category ALSO has to be listed on a channel in `TASK_CHANNEL_DEFINITIONS` or it will not route anywhere. Real callers: `proposals/approvalWorkflow.ts`, `feedback/feedbackTaskService.ts`, CF `onFeedbackResolved`.
- **DEAD:** `lib/notifications/` (`createNotification` → `notifications` collection). No callers; `NotificationCenter` is never mounted; the `NotificationType` union in `@vapour/types/notification.ts` is referenced only inside its own file. Writing here produces an invisible notification.
- **DEAD:** the AppBar bell (`components/dashboard/AppBar.tsx`) is a static icon — no `onClick`, no badge, no query. `TaskNotificationBell` exists but is not mounted anywhere.

Always add notifications through `createTaskNotification` (rule 32).

### Materials data model — flat piping vs. plate variants

Two shapes live in the `materials` collection. Getting this wrong silently returns zero rows:

- **Piping (pipes, flanges, fittings) is FLAT** — one document per NPS + schedule/rating, with the dimensions on the document itself (`nps`, `schedule`/`pressureClass`/`fittingType`, `outsideDiameter_mm`, `wallThickness_mm`, `weightPerMeter_kg`, …). The old parent-doc + `materials/{id}/variants` subcollection shape is dead: the superseded parents carry `isMigrated: true` and hold the only surviving variants. **Never walk the `variants` subcollection for piping.**
- **Plates still use the variants model** — one parent per grade, thickness as variants. `usesVariantModel(category)` in `@vapour/types` is the test.

Read through `lib/materials/queries.ts` — `queryMaterials` (drops `isMigrated` parents), `searchMaterials`, `queryMaterialsByFamily`, `queryPipingFamilies`. Derive category lists from `MATERIAL_CATEGORY_GROUPS` (`@vapour/types`), never a hardcoded array — a hardcoded list is how duplex/super-duplex pipes and slip-on/blind flanges went missing from their module pages until `c816ab8e`. Indexed by `(category ASC, materialCode ASC)`.

Canonical pages: [`/materials/pipes`](../apps/web/src/app/materials/pipes/page.tsx), `/materials/flanges`, `/materials/fittings`.
